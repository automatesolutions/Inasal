🎯 Overview: What Happens When User Logs In

Step-by-Step Flow:
1. User enters phone → Frontend sends OTP request
2. User enters OTP → Backend creates profile + starts personality analysis
3. User goes to /chat → Frontend loads welcome message
4. Backend generates recommendations → Returns to frontend
5. Frontend displays welcome + recommendations

Step 4: Backend Generates Welcome Message

📍 Backend Route: backend/app/routes/chat_routes.py

@router.get("/welcome") async def get_welcome_message(current_user: dict = Depends(get_current_user)): user_id = current_user["user_id"] # ⏳ WAIT for personality analysis to complete (up to 30 seconds) personality = None for attempt in range(60): # 60 attempts × 0.5s = 30 seconds max profile = await profile_service.get_profile(user_id) if profile: # Check if personality has been analyzed (any trait > 0.5) traits = profile.personality.model_dump() if any(v > 0.5 for v in traits.values()): personality = profile.personality break await asyncio.sleep(0.5) # Wait 0.5 seconds between checks # Generate welcome message text from app.welcome_message_service import WelcomeMessageService welcome_service = WelcomeMessageService() welcome_text = await welcome_service.generate_welcome_message( user_name=profile.name, personality=personality ) # Get ALL recommendations from app.comprehensive_recommendations import ComprehensiveRecommendationsService recommendations_service = ComprehensiveRecommendationsService() recommendations = await recommendations_service.get_all_recommendations(user_id) return { "content": welcome_text, "recommendations": recommendations, "personality_summary": welcome_service.get_personality_summary(personality) }

💡 What This Does:

  • Extracts user_id from JWT token
  • Polls for personality analysis (waits up to 30 seconds)
  • Gets user profile (from InstantDB → BigQuery → cache)
  • Generates personalized welcome message using LLM
  • Fetches recommendations for all categories
  • Returns everything to frontend

📍 Example: How Hotels Are Filtered: backend/app/comprehensive_recommendations.py

async def _get_hotels(self, profile, location, curated_details): # 1. Load scraped content from InstantDB scraped_content = await self._get_scraped_content_for_category("accommodation_hotels") seen_names = set() # Track duplicates formatted_hotels = [] for item in scraped_content: hotel_name = item.get("hotel_name") or item.get("name") # FILTER 1: Skip if no hotel name if not hotel_name: continue # FILTER 2: Skip general articles/blog posts if self._is_general_article_or_guide(hotel_name, description): continue # Skip "17 Tourist Spots in Bacolod..." type articles # FILTER 3: Remove duplicates name_key = " ".join(hotel_name.lower().strip().split()) if name_key in seen_names: continue seen_names.add(name_key) # FILTER 4: Calculate match score with personality match_score = self._calculate_match_score(rec_item, profile.personality) if match_score <= 0.5: # Only show if match > 50% continue # Format and add to list formatted_hotels.append(formatted_item) return formatted_hotels

💡 What This Does:

  • Loads hotel data from InstantDB (scraped from Google Sheet)
  • Filters out articles/blog posts (only specific hotels)
  • Removes duplicates by normalized name
  • Calculates personality match score (0.0 to 1.0)
  • Only includes hotels with match score > 50%
  • Returns filtered list

📡 Scrape Data and LLM Flow (Detailed)

This section explains exactly how data is collected (search + optional scrape) and how it is passed through the LLM to produce personality traits.

Overview: Two Data Paths

The pipeline tries Path A first (social profile search + optional page scrape). If that returns no usable data, it uses Path B (Google SERP search only). Both paths end with the same LLM steps: summarize → analyze personality.

  • Path A: Search for Facebook/Instagram profiles (Bright Data) → optionally scrape profile page (Scrapy + Bright Data proxy) → LLM summarizes scraped data → LLM extracts traits
  • Path B (primary in practice): Google SERP search for the person's name (Bright Data) → LLM summarizes SERP snippets → LLM extracts traits

Step 1: Search for Social Profiles (Scraper)

File: backend/app/social_scraper.py

Function: SocialMediaScraper.search_social_profiles(first_name, last_name, phone_number)

What it does:

  • Uses Bright Data (self.bright_data = bright_data_client) to run Google searches, not direct Facebook/Instagram APIs.
  • First query: "{first_name} {last_name}" site:facebook.com → bright_data_client.search_public(source="google", query=facebook_query, limit=5)
  • Second query: "{first_name} {last_name}" site:instagram.com → same search_public("google", instagram_query, 5)
  • Returns: { "facebook_profiles": [...], "instagram_profiles": [...] } – each item has title, snippet, url from search results.

Code reference: social_scraper.py lines ~273–317.

Step 2: Optional – Scrape Profile Page (Scrapy)

File: backend/app/social_scraper.py

Function: scraper.scrape_profile_data(profile_url, "facebook" | "instagram")

What it does:

  • Runs a Scrapy spider (FacebookProfileSpider or InstagramProfileSpider from app/scrapers/social_media_spider.py) to fetch the profile page HTML.
  • Uses Bright Data Residential Proxy (_get_bright_data_proxy()) so requests come from residential IPs; configured via bright_data_residential_username, bright_data_residential_password, bright_data_residential_endpoint in settings.
  • Returns a dict like { "bio", "posts_content", "interests", "location", ... } if scraping succeeds. Often fails (Facebook/Instagram block bots), so pipeline falls back to SERP.

Code reference: social_scraper.py scrape_profile_data and _run_scrapy_spider; proxy in _get_bright_data_proxy().

Step 3: SERP-Only Path – Google Search for the Person

File: backend/app/personality_pipeline.py

When: Used when scraped_data is empty or not meaningful (no bio, posts, or interests).

What it does:

  • Imports bright_data_client from app.bright_data_client.
  • Builds query: google_query = f"{first_name} {last_name}" (optionally appends phone_number).
  • Calls bright_data_client.search_public(source="google", query=google_query, limit=10).
  • Gets back serp_results with results array: each item has title, snippet, url (search result snippets, not full page content).

Code reference: personality_pipeline.py lines ~122–139.

Step 4: Pass Data to LLM – Summarize

File: backend/app/personality_analyzer.py

LLM instance: PersonalityAnalyzer uses self.llm = get_chat_llm(temperature=0.3) from app/llm_factory.py (e.g. OpenAI).

Path A – Scraped data:

  • Function: analyzer.summarize_social_data(scraped_data)
  • Input: dict with bio, posts_content, interests, location from Scrapy.
  • Builds a prompt asking the LLM to summarize the profile into interests, travel preferences, social behavior, activity preferences, personality indicators.
  • Call: response = await self.llm.ainvoke(summary_prompt) → returns a text summary.

Path B – SERP results:

  • Function: analyzer.summarize_google_search_results(serp_results, first_name, last_name)
  • Input: serp_results["results"] – list of { title, snippet, url }.
  • Builds search_context from top 10 results (title + snippet + URL per result), then a prompt asking the LLM to analyze the search results for that person and produce a personality profile (interests, travel, social behavior, activity preferences, personality indicators).
  • Call: response = await self.llm.ainvoke(summary_prompt) → returns a text summary.

Code reference: personality_analyzer.py – summarize_social_data (~18–74), summarize_google_search_results (~240–315).

Step 5: LLM – Extract Personality Traits

File: backend/app/personality_analyzer.py

Function: analyzer.analyze_personality_from_summary(summary)

Input: The text summary from Step 4 (either from scraped data or from SERP).

What it does:

  • Builds a long analysis_prompt that includes the summary and instructs the LLM to assign scores 0.0–1.0 for: adventurous, cultural, foodie, nature_lover, history_buff, social, with rules (e.g. "sports" → adventurous 0.7–0.9, "cultural" → cultural 0.7–0.9).
  • Asks the LLM to return only valid JSON with those six keys plus optional reasoning.
  • Call: response = await self.llm.ainvoke(analysis_prompt).
  • Parses the response (strips markdown code blocks if present, extracts JSON), then builds a PersonalityTraits model and clamps each score to 0.0–1.0.

Output: PersonalityTraits(adventurous=..., cultural=..., foodie=..., nature_lover=..., history_buff=..., social=...).

Code reference: personality_analyzer.py analyze_personality_from_summary (~75–196).

Step 6: Save Personality – Cache and InstantDB

File: backend/app/personality_pipeline.py (after LLM returns)

What it does:

  • profile_service._set_cached_personality(user_id, personality) – stores in in-memory _personality_cache so the welcome endpoint can return correct traits immediately even before InstantDB is updated.
  • profile_service.update_personality(user_id, personality) → user_profile.py calls instantdb_client.update_user_profile(user_id, update_data) to persist to InstantDB.

❌ The BigQuery Streaming Buffer Problem

Issue: When user profiles are created via streaming insert, BigQuery keeps them in a streaming buffer for 90+ minutes. During this period, UPDATE or DELETE operations are NOT ALLOWED.

Symptom What Happened Impact
Backend shows analyzed traits Adventurous: 0.7, Social: 0.9 ✅ Analysis works
Try to save to BigQuery UPDATE query fails ❌ Error: "streaming buffer"
BigQuery table still has defaults Adventurous: 0.5, Social: 0.5 ❌ Traits not saved
Frontend requests profile Gets 0.5, 0.5 from BigQuery ❌ Shows wrong personality

✅ The Three-Layer Solution

Layer 1: In-Memory Cache

File: backend/app/user_profile.py

Purpose: Store analyzed personality immediately when analysis completes. get_profile() returns from cache when DB has all defaults (0.5).

# When DB returns all 0.5, check cache: if all_defaults: cached = self._get_cached_personality(user_id) if cached: return profile with cached personality # Frontend gets correct traits immediately
  • Dictionary: _personality_cache[user_id] = PersonalityTraits
  • Set by personality_pipeline after LLM analysis
  • Cleared after BigQuery successfully updates

Layer 2: Background Retry System

File: backend/app/bigquery_retry_queue.py

Purpose: Automatically retry BigQuery updates with exponential backoff. Started in main.py lifespan.

# Started on app startup (main.py lifespan): background_retry_task = start_background_retry_task() # Runs forever, every 2 minutes: async def background_retry_task(): while True: await asyncio.sleep(120) # Wait 2 min pending = await retry_queue.get_pending_retries() for user_id, traits in pending.items(): success = await bigquery_client.update_user_profile(user_id, traits) if success: await retry_queue.mark_success(user_id)
  • Runs every 2 minutes
  • Exponential backoff: 2, 5, 10, 20, 30, 60 min
  • Gives up after 6 hours or 12 attempts

Layer 3: Better SQL Statement

File: backend/app/bigquery_client.py

Purpose: Use MERGE instead of DELETE+UPDATE for better streaming buffer handling

  • MERGE handles both INSERT and UPDATE
  • Better compatibility with streaming buffer
  • Reduces failures during buffer period

💡 Key Insight: Why This Works

BigQuery's streaming buffer is NOT a bug — it's a design feature that ensures:

  • Data consistency
  • Performance optimization
  • Transaction safety

Our solution doesn't try to bypass it. Instead, we:

  • Accept the limitation exists
  • Use cache for immediate availability
  • Retry when buffer expires
  • Ensure data eventually persists

This is the industry-standard pattern used by AWS, Google Cloud, and Microsoft Azure for handling streaming data inserts.

async def get_profile(self, user_id: str) -> Optional[UserProfile]: """ Gets user profile with this priority: 1. InstantDB (fastest, real-time) 2. BigQuery (persistent storage) 3. 2. How Personality Matching Works

File: backend/app/comprehensive_recommendations.py

def _calculate_match_score(self, item: Dict, personality) -> float: """ Calculates how well an item matches user's personality. Returns score from 0.0 to 1.0 (0% to 100% match). """ # Check if item has personality keywords (extracted by LLM from scraped content) if "personality_keywords" in item: pk = item["personality_keywords"] # pk looks like: {"adventurous": 0.8, "foodie": 0.6, "cultural": 0.3} total_score = 0.0 count = 0 # Compare each trait for trait_name in ["adventurous", "cultural", "foodie", "nature_lover", "history_buff", "social"]: item_value = pk.get(trait_name, 0.0) # Item's trait value user_value = getattr(personality, trait_name, 0.5) # User's trait value # Calculate match using TWO methods: # 1. Magnitude Match (70% weight): Both high = good match magnitude_match = user_value * item_value # 2. Similarity (30% weight): Close values = good match similarity = 1.0 - abs(user_value - item_value) # Combine both combined_score = magnitude_match * 0.7 + similarity * 0.3 total_score += combined_score count += 1 # Average all traits score = total_score / count if count > 0 else 0.5 # Scale to 0.1-1.0 range (10%-100%) scaled_score = 0.1 + (score * 0.9) return min(1.0, max(0.1, scaled_score)) # Fallback: Use type/tags matching return 0.5

💡 Example Calculation:

User: adventurous=0.8, foodie=0.6 Hotel: personality_keywords={"adventurous": 0.9, "foodie": 0.7} For "adventurous": magnitude_match = 0.8 × 0.9 = 0.72 similarity = 1.0 - |0.8 - 0.9| = 0.9 combined = 0.72 × 0.7 + 0.9 × 0.3 = 0.774 For "foodie": magnitude_match = 0.6 × 0.7 = 0.42 similarity = 1.0 - |0.6 - 0.7| = 0.9 combined = 0.42 × 0.7 + 0.9 × 0.3 = 0.594 Average = (0.774 + 0.594) / 2 = 0.684 Scaled = 0.1 + (0.684 × 0.9) = 0.716 = 71.6% match
