Bacolod Tourist – System Workflow

Detailed flowcharts and code walkthrough so you can see exactly how requests move through the app. This guide is intentionally verbose for learning.

1. High-level request flow

Every user action (login, chat, recommendations) follows this path: the browser sends HTTP requests to your Next.js app; Next.js (or the client) calls the FastAPI backend; the backend talks to internal services (Redis, InstantDB, Make.com, BigQuery, etc.) and returns JSON. The frontend never holds database credentials or talks to Redis directly—all of that stays on the server.

Why this matters: The frontend never talks to Redis or the database directly. All sensitive work (tokens, profile creation, AI) happens in the backend so secrets and logic stay server-side.

What each layer does

  • User / Browser: The person using the app. Actions (e.g. “Log in with phone”, “Send chat message”) become HTTP requests. The frontend often sends these with Authorization: Bearer <JWT> after login.
  • Next.js (frontend): Serves the React UI and can proxy or call the backend. API calls typically go to a base URL like https://your-api.com or http://localhost:8000. The frontend stores the JWT (e.g. in localStorage) and sends it on every request that needs authentication.
  • FastAPI (backend): Defines routes under /api/auth/*, /api/chat, /api/recommendations, etc. It validates the JWT (for protected routes), reads/writes Redis and InstantDB, calls Make.com webhooks or in-app services, and returns JSON. All environment secrets (Redis URL, JWT secret, Make.com webhook URLs) live in backend config.
  • Services: Redis (OTP storage, optional caching), InstantDB (user profiles and personality), Make.com (optional chat/recommendations workflows), BigQuery and Cloud Storage (analytics and assets). The backend is the only component that connects to these.

2. Auth workflow (phone OTP)

Phone login is a two-step process: (1) user enters phone number and name, backend stores an OTP in Redis and returns success; (2) user enters the OTP, backend verifies it, creates a user profile in InstantDB, returns a JWT and user_id, and starts the personality analysis pipeline in the background so the user does not wait for it. In development the app uses a fixed dummy OTP (000000); in production you would send a real OTP via SMS (e.g. Twilio).

Step-by-step: what happens in order

  1. User requests OTP: Frontend sends POST /api/auth/send-otp-phone with body { "phone_number": "09XX...", "first_name": "...", "last_name": "..." }. Phone is validated with a Philippine format regex (+63 / 0 + 9 digits).
  2. Backend stores OTP: Backend normalizes the phone to +63XXXXXXXXXX, generates an OTP (in dev it is always 000000), then stores two keys in Redis: otp:phone:+63XXXXXXXXXX = OTP string, and otp:meta:phone:+63XXXXXXXXXX = JSON { "first_name", "last_name", "phone_number" }. Both keys use expire=600 (10 minutes). Response to client: { "message": "OTP sent...", "dummy_otp_hint": "Use OTP: 000000 to verify" }.
  3. User submits OTP: Frontend sends POST /api/auth/verify-otp-phone with { "phone_number", "otp", "first_name", "last_name" }.
  4. Backend verifies: Backend reads stored_otp = redis_client.get(otp_key). If missing or wrong (and not dev dummy), it returns 400/401. If correct, it deletes otp_key and meta_key so the OTP cannot be reused.
  5. Profile creation: Backend generates a new user_id (UUID), builds user_email = "+63...@phone.local" and user_name from first/last name, then calls profile_service.create_profile(user_id, email, name, phone_number, first_name, last_name). That writes the profile to InstantDB (and optionally BigQuery).
  6. Background personality task: Backend calls asyncio.create_task(_run_personality_analysis()). That task waits ~1 second, optionally retries get_profile(user_id) up to 5 times, then calls analyze_personality_from_social_media(user_id, first_name, last_name, phone_number). The HTTP response is not waiting for this to finish.
  7. Response to client: Backend creates a JWT with create_access_token(data={"sub": user_id, "email": user_email, "phone_number": normalized_phone}) and returns { "access_token", "token_type": "bearer", "user_id", "email", "phone_number", "personality_analysis_status": "in_progress" }. The frontend stores access_token and user_id and uses the token in the Authorization header for later requests.

Redis keys and expiration (detail)

  • otp:phone:+639XXXXXXXXXX — value is the 6-digit OTP string. TTL = OTP_EXPIRATION_SECONDS (600 seconds = 10 minutes). Deleted immediately after successful verification.
  • otp:meta:phone:+639XXXXXXXXXX — value is JSON: {"first_name","last_name","phone_number"}. Same TTL. Used during verify to fill in name if the client did not send it again. Also deleted after verification.

JWT payload (what’s inside the token)

The backend uses app.auth.create_access_token(data) which adds an exp claim and signs with settings.jwt_secret_key. The payload typically contains:

  • sub — the user_id (UUID). This is the main identifier for “who is this user?” on every request.
  • email — for phone users this is +63...@phone.local; used for display or compatibility.
  • phone_number — normalized +63....
  • exp — expiration timestamp (e.g. 24 hours from issue, from settings.jwt_expiration_hours).

Protected routes use get_current_user, which reads Authorization: Bearer <token>, decodes the JWT, and returns {"user_id": payload["sub"], "email": payload.get("email")}. If the token is missing or invalid, the route returns 401.

Code: where OTP is stored and verified

Send-OTP stores the OTP and metadata in Redis with a 10-minute TTL. Verify reads the OTP, compares it (with special handling for dev dummy OTPs like 000000), deletes both keys, creates the profile, schedules the personality task, and returns the JWT.

await redis_client.set(meta_key, json.dumps({"first_name": request.first_name, ...}), expire=600)
# auth_routes.py – verify_otp_phone (simplified)

if stored_otp and stored_otp != request.otp: raise HTTPException(401, "Invalid OTP")
await redis_client.delete(otp_key) # one-time use

Background task: _run_personality_analysis() waits ~1 second, optionally retries get_profile(user_id), then calls analyze_personality_from_social_media(...). The user gets the JWT immediately; personality is written to InstantDB later and used for recommendations and chat.

3. Personality pipeline (Search → Scrape → Summarize → Analyze → Store)

After login, the backend runs the personality pipeline in the background. Its goal is to infer six personality traits (adventurous, cultural, foodie, nature_lover, history_buff, social) as floats between 0 and 1, then save them and a short text summary to the user’s profile in InstantDB. The pipeline first tries to get data from social profiles (search then scrape); if that yields nothing useful, it uses Google search results via Bright Data SERP, summarizes them with an LLM, and then runs a second LLM call to turn the summary into trait scores. If SERP also fails, it infers traits from a short context (e.g. “tourism app user in Bacolod”) or falls back to moderate default scores so the profile is never left with all zeros.

Step-by-step: what the pipeline does

  1. Search for profiles: SocialMediaScraper.search_social_profiles(first_name, last_name, phone_number) returns a dict with keys like facebook_profiles and instagram_profiles, each a list of items with url. These URLs are candidates to scrape.
  2. Scrape (optional): If there is a Facebook profile URL, the code calls scrape_profile_data(profile_url, "facebook"); if that returns nothing, it tries the first Instagram profile. In practice, scraping often returns nothing (anti-bot), so the pipeline is designed to rely on the next step.
  3. SERP fallback (main path): If scraped_data is missing or empty, the code uses bright_data_client.search_public(source="google", query=first_name + " " + last_name, limit=10). That returns a list of search results (title, snippet, URL). Those URLs are collected into source_links for the profile.
  4. Summarize: If scraped data existed and had content, analyzer.summarize_social_data(scraped_data) produces a text summary. Otherwise analyzer.summarize_google_search_results(serp_results, first_name, last_name) turns the SERP snippets into one summary string. Both use an LLM.
  5. Analyze personality: analyzer.analyze_personality_from_summary(summary) returns a PersonalityTraits Pydantic model: six floats (0–1) for adventurous, cultural, foodie, nature_lover, history_buff, social. Defaults are 0.5 if the LLM does not specify.
  6. Store: profile_service.update_personality(user_id, personality, characteristics_summary=summary, source_links=source_links) writes the traits and summary to InstantDB (and optionally caches in memory). Later, get_profile(user_id) returns a UserProfile that includes this personality and characteristics_summary.

PersonalityTraits model (data shape)

Defined in app.user_profile. All fields are float in [0.0, 1.0], default 0.5:

  • adventurous — openness to risk, new experiences
  • cultural — interest in arts, heritage, local culture
  • foodie — interest in food and dining
  • nature_lover — interest in outdoors, nature, parks
  • history_buff — interest in history, museums, landmarks
  • social — interest in socializing, nightlife, group activities

Recommendations use these scores to rank or filter places (e.g. higher foodie boosts restaurants and food tours).

Fallbacks when data is missing

If SERP returns no results (e.g. Bright Data not configured or rate limit), the code builds a short context_summary from the user’s name and the fact they use a tourism app in Bacolod, then calls analyze_personality_from_summary(context_summary) to get at least some non-zero traits. If that or any step fails with an exception, the pipeline saves a PersonalityTraits with moderate defaults (e.g. 0.65, 0.7, 0.65, 0.55, 0.45, 0.75) so the profile is never left with all zeros.

Code: pipeline entry and SERP fallback

The single entry point is analyze_personality_from_social_media(user_id, first_name, last_name, phone_number). It coordinates the scraper, Bright Data client, and PersonalityAnalyzer, then calls update_personality with the final traits and summary.

Traits stored: PersonalityTraits and characteristics_summary are written to InstantDB and returned by get_profile(user_id). The recommendation and chat flows read this profile to personalize results and responses.

4. Chat workflow

When the user sends a chat message, the frontend calls POST /api/chat with the request body { "message": "user text" } and the Authorization: Bearer <JWT> header. The backend uses the JWT to get user_id (via get_current_user). It then tries the Make.com chat webhook first: if settings.make_webhook_chat is set, it POSTs { "user_id", "message" } to that URL and expects a JSON response with a response field. If the webhook is missing or the request fails (network error, non-2xx, or no response in the body), the code falls back to the in-app ChatAgent (LangChain), which uses the same user_id and message to generate a reply. The response to the client is always { "response": "string" }.

Request: POST /api/chat, headers Authorization: Bearer <JWT>, body { "message": "user's text" }. The route depends on get_current_user, which decodes the JWT and provides user_id (and optionally email).

Make.com path: make_client.send_chat_message(user_id, message) does POST make_webhook_chat with JSON { "user_id", "message" }, timeout 60s. Expected response: JSON object with a response key (the assistant reply string). If the status is not 2xx or an exception is raised, the code catches it and falls through.

Fallback path: ChatAgent() is from app.chat_agent. Its chat(message, user_id) method uses LangChain (and possibly the user’s profile/personality) to generate a reply. The return value is a single string.

Response: Always 200 with body { "response": "assistant reply string" }. If neither Make nor ChatAgent is available (e.g. LangChain not installed and no webhook), the route would raise 503; in practice the fallback is used when the webhook is missing or fails.

5. Recommendations workflow

Recommendation endpoints return personalized lists of places (hotels, restaurants, entertainment, tourist spots, and optionally “secret” spots). The backend identifies the user via the JWT (get_current_user → user_id), loads the full profile from InstantDB (including personality and preferences), then either calls a Make.com recommendations webhook with user_id or uses the in-app ComprehensiveRecommendationsService to score and select items from the app’s data. The response normalizes items to a common shape (e.g. name, url, description, match_score, category) so the frontend can display them consistently.

How the profile is used

Protected recommendation routes use current_user: dict = Depends(get_current_user) to get user_id. They then call profile_service.get_profile(user_id), which reads from InstantDB (and optionally BigQuery fallback). The returned UserProfile includes personality (the six trait scores) and preferences, which the recommendation logic uses to rank or filter places—for example, higher foodie boosts restaurants and food-related spots.

Where recommendations come from

Depending on configuration, the backend may:

  • Make.com: Call make_client.get_recommendations(user_id), which POSTs to settings.make_webhook_recommendations with { "user_id" }. The webhook is expected to return a structure that the route then normalizes (e.g. mapping rating to match_score).
  • In-app: Use ComprehensiveRecommendationsService (and possibly the recommendation engine) to pull places from the app’s data store and score them using the user’s personality and preferences. Results are returned in the same shape as the Make path for a consistent API.

Response shape typically includes lists such as hotels, restaurants, entertainment, tourist_spots, secret_recommendations, each a list of objects with name, url, description, match_score (0–1), and optional category, image.

6. Personality-based hotel selection algorithm

When a user requests hotel recommendations, the system uses their personality traits to calculate a match score for each hotel. Hotels are filtered to only include those with a match score above 50%, ensuring personalized recommendations that align with the user's preferences. This section explains the complete algorithm with detailed mathematical calculations.

Data flow: From InstantDB to match score

Step-by-step algorithm

  1. Load user personality: profile = await profile_service.get_profile(user_id) retrieves the user's personality traits from InstantDB. Each trait is a float between 0.0 and 1.0.
  2. Load hotels from InstantDB: scraped_content = await self._get_scraped_content_for_category("accommodation_hotels") loads all hotels from the InstantDB collection. Each hotel includes personality_keywords extracted during scraping.
  3. Filter invalid hotels: Skip hotels without names, general articles/guides, test entries, and duplicates.
  4. Calculate match score: For each valid hotel, call match_score = self._calculate_match_score(rec_item, profile.personality).
  5. Filter by threshold: Only include hotels where match_score > 0.5 (50%).
  6. Return results: Format and return filtered hotels sorted by match score.

The match score calculation algorithm

The core algorithm compares user personality traits with hotel personality keywords. It uses a two-part scoring system:

Formula for each trait:

# For each of the 6 personality traits:
user_val = profile.personality.trait # e.g. adventurous = 0.8
item_val = hotel.personality_keywords["trait"] # e.g. adventurous = 0.7

# Part 1: Magnitude Match (70% weight)
magnitude_match = user_val × item_val # 0.8 × 0.7 = 0.56

# Part 2: Similarity (30% weight)
similarity = 1.0 - |user_val - item_val| # 1.0 - |0.8 - 0.7| = 0.9

# Combined score for this trait
combined_score = (magnitude_match × 0.7) + (similarity × 0.3)
# (0.56 × 0.7) + (0.9 × 0.3) = 0.392 + 0.27 = 0.662

Final score calculation:

# Average across all 6 traits
total_score = sum(combined_score for each trait)
count = number of traits with valid values
score = total_score / count

# Scale to 0.1-1.0 range (10% to 100%)
scaled_score = 0.1 + (score × 0.9)
# Ensures minimum 10% visibility
return min(1.0, max(0.1, scaled_score))

total = 0.662 + 0.336 + 0.774 + 0.681 + 0.296 + 0.576
total = 3.426
count = 6

Filtering decision:

# Since 0.614 > 0.5, this hotel is INCLUDED in recommendations

Why this algorithm works

Magnitude Match (70% weight): Rewards hotels where both user and hotel have high trait values. For example, if a user is highly adventurous (0.9) and a hotel offers adventure activities (0.8), the magnitude match is 0.72, indicating a strong alignment.

Similarity (30% weight): Rewards hotels where trait values are close to the user's values. This ensures that even if both values are moderate, a close match (e.g., user 0.6, hotel 0.65) scores better than a mismatch (user 0.6, hotel 0.2).

Combined approach: The 70/30 split ensures that high-magnitude matches (both high) are prioritized while still rewarding similarity. This creates a balanced recommendation system that considers both intensity and alignment.

# comprehensive_recommendations.py - _calculate_match_score()
def _calculate_match_score(self, item: Dict, personality) -> float:
    if "personality_keywords" in item:
        pk = item["personality_keywords"]
        traits = ["adventurous", "cultural", "foodie", "nature_lover", "history_buff", "social"]
        total = 0.0
        count = 0
        for t in traits:
            item_val = pk.get(t)
            if item_val is not None:
                user_val = getattr(personality, t, 0.5)
                magnitude_match = user_val × item_val
                similarity = 1.0 - abs(user_val - item_val)
                combined_score = magnitude_match × 0.7 + similarity × 0.3
                total += combined_score
                count += 1
    if count > 0:
        score = total / count
        scaled_score = 0.1 + (score × 0.9)
        return min(1.0, max(0.1, scaled_score))

Summary

The personality-based hotel selection algorithm ensures that:

  • Hotels are loaded from InstantDB with their personality_keywords already extracted during scraping
  • Each hotel is scored by comparing user personality traits with hotel personality keywords
  • The scoring considers both magnitude (both high = strong match) and similarity (close values = better alignment)
  • Only hotels with match scores above 50% are included in recommendations
  • The algorithm is transparent and mathematically sound, providing explainable recommendations

Important models

  • PersonalityTraits: adventurous, cultural, foodie, nature_lover, history_buff, social (float 0–1, default 0.5).
  • UserProfile: user_id, email, phone_number, first_name, last_name, name, personality, preferences, characteristics_summary, source_links, travel_history, created_at, updated_at.
  • JWT payload: sub (user_id), email, phone_number, exp.
